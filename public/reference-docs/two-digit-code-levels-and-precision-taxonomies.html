Two-Digit Code Levels and Precision Taxonomies

An investigation, a worked example and a conclusion for Taxonomy BuilderTM

Item Detail
Author Dr James A Robertson, The ERP Doctor assisted by Claude.AI
Date 23 November 2026
Purpose Record the investigation into two-digit code levels and the resulting rule for Taxonomy BuilderTM

About this document

In response to questions about Taxonomy BuilderTM accommodating code schemes with two digits per code level, research was undertaken by Claude in the context of the disciplines and rules advocated by the ERP Doctor. The following presents the findings of that research and analysis.

1. Conclusion

Taxonomy BuilderTM will continue to allow one character per code level. It will not be modified to allow two-digit (or wider) codes per level.

The tool exists to build precision taxonomies that comply with Miller’s Law and ERP Doctor standards. It does not exist to host or reproduce existing code schemes that do not. Such lists remain alongside a precision taxonomy and are cross-mapped onto it where necessary.

A single character does not limit capacity as much as it first appears: numeric codes give 9 items per level, and alpha characters give a further 26 upper-case and 26 lower-case where a level genuinely needs more.

2. Background: the current rules

  • One character per level, with delimiters between selected columns if required as a design principle.

  • The character may be numeric, alpha or alphanumeric. Numeric gives 9 codes per level; upper-case alpha gives 26 and lower-case alpha a further 26. The GL and the dimensions are recommended to use numeric only, because their codes are used by people working largely on the numeric keypad, and alpha is inefficient from a keyboard-dexterity perspective.

  • Between 5 and 9 items at any level is the guiding target, ideally about 7 (Miller’s Law). Fewer than about 5 tells the reader little; more than about 9 becomes confusing. Where logical grouping indicates fewer than 5 or more than 9, this can be accommodated with caution.

  • Structural levels are named in ALL CAPS; posting items are named in Proper Case.

  • Gap coding: unused codes are left free so that items can be added later without renumbering.

3. Investigation: schemes that use two-digit levels

A web search found the following established schemes. Each example below was checked against a source page that was opened – links at the end of this document.

Scheme Code structure Verified example
UNSPSC Four levels of two digits, no separators in the 8-digit form. Unused levels are padded with 00. 10-10-15-01 is Cats, under Livestock (10-10-15), under Live animals (10-10), under Live Plant and Animal Material (10).
MasterFormat Pairs of digits separated by spaces. Level 3 adds .nn. 06 41 93 is Cabinet and Drawer Hardware, under Architectural Wood Casework, under Wood, Plastics, and Composites.
ICS (International Classification for Standards) Mixed widths: nn.nnn.nn, with an unofficial -nn fourth level. 43.040.20 is Lighting, signaling and warning devices. 35.220.20-10 is Magnetic tapes.
Harmonized System (HS) Cumulative prefixes, with a dot after the 2nd digit in headings and after the 4th and 6th in subheadings. 06 Live trees and other plants; 06.01 Bulbs, tubers etc.; 0601.10 Bulbs, tubers etc., dormant.
Schedule B (US Census Bureau) The HS extended to ten digits. 0713.10.4020 is Green peas.
Uniclass 2 (proposal) Table prefix plus two-digit levels joined by hyphens. Ee-30-65-88, given as an illustration with no title.

The UNSPSC example, level by level:

Code Level Title
10 Segment Live Plant and Animal Material
10-10 Family Live animals
10-10-15 Class Livestock
10-10-15-01 Commodity Cats

Limits of this research. The Uniclass 2015 definition pages could not be opened, so only the Uniclass 2 proposal is cited.

Observations:

  • The width, separator and padding all differ from scheme to scheme: no separator, space, dot or hyphen.

  • UNSPSC pads unused levels with 00; HS shows the full prefix at each level rather than only the segment for that level.

  • Two-digit levels allow up to 99 siblings, but nothing in the width requires that many.

4.2 The problems with the original list

  • Forty siblings sit at one level, against a guiding target of 5 to 9.

  • The codes are not contiguous (01, 03, 07, 11, 13 …), so the code does not say how many fields exist or what is missing.

  • Related fields are scattered. Transport engineering (43 to 49) and Packaging and distribution (55) are separated by Materials handling (53); there is no single code that means “all transport”.

  • To analyse by theme, a user must maintain a list of codes, for example 43, 45, 47, 49 and 55 for transport, and then write a query against that list.

4.3 The reclassified taxonomy

The 40 fields were grouped into 9 structural groups, the numeric maximum for level 1, keeping to Miller’s Law as far as logical grouping allows. Forty items cannot give 9 groups of 5 or more (9 × 5 = 45), so some groups hold fewer than 5. Level 1 is structural (ALL CAPS); level 2 is posting (Proper Case). The original ICS code is retained as a cross-reference. Item names are the ICS titles exactly as published, in Proper Case.

Each level 1 heading carries a full stop in the Level 2 column. A posting code is two characters: the Level 1 character followed by the Level 2 character. For example, 51 is Road Vehicles Engineering.

4.4 What the example shows

  • Querying. “All transport” becomes every code that starts with 5. No list of codes has to be maintained.

  • Code length. The new code is still two characters, but it now carries two levels of hierarchy instead of one flat level.

  • Growth and gap coding. Every group has at least three unused digits left as gaps for new items, any grouping could be gap coded if required, and alpha characters would extend any group further.

  • Completeness. A structured list more readily enables a comprehensive code scheme. The ICS list is evidently incomplete: examining it as groups shows that many other items could realistically be added, and in a structured taxonomy each new item has an obvious home, whereas a flat list gives no indication of what is missing.

  • Judgement calls. Group 2 pairs health and environment with agriculture and food as a life-and-environment grouping. Domestic and commercial equipment, entertainment, sports (97) fits poorly anywhere and sits in group 9 with construction and defence. Both are reasonable alternatives to debate.

  • Scope. Only the 40 top-level fields were classified. ICS groups and subgroups below them (for example 43.040) would need a third level, whose item counts would be judged against the same guiding target.

  • This analysis is indicative and is not intended to be definitive or exhaustive. It was undertaken to examine whether having two digits per code level offered any material advantage – it is concluded that it does not.

5. Pros and cons of two-digit code levels

5.1 Arguments for

  • Mirrors external standards (UNSPSC, MasterFormat, ICS, HS) without remapping.

  • Up to 99 siblings per level, so a large flat list needs fewer levels.

  • Gap coding with 10, 20, 30 leaves room to insert between existing items.

  • Matches legacy ERP account structures that already use fixed-width segments.

5.2 Arguments against

  • Sloppy coding. A two-character code at one level encourages what the ERP Doctor terms “sloppy coding”, whereas two single-character code elements encourage structured discipline. A two-character code also hides two levels of hierarchy in one field: the code 43 does not say what 4 or 3 means, while two single-character elements make each level explicit and queryable.

  • It invites the flat list. Allowing 99 siblings makes a 40-item level feel acceptable, which is exactly the ICS problem. The width stops enforcing the discipline, so the tool’s warnings would be the only control.

  • Parsing and queries. Mixed widths need delimiters or a fixed layout to parse, and a test for “starts with 5” becomes “positions 1 and 2 equal 51”.

  • More configuration. Per-level width is one more setting to define, validate and keep consistent across files.

  • The capacity argument is already met. A single character can be numeric (9), upper-case alpha (26) or lower-case alpha (26), so a level that genuinely needs more than 9 items can have them without a second character. Gap coding is also available by leaving unused characters free.

5.3 Assessment

For building new precision taxonomies, two digits per level adds nothing and weakens the discipline. A two-digit level is not poorly structured in itself: UNSPSC is hierarchical, with each pair of digits adding a level, although its levels are not held to the 5 to 9 target. What was clumsy in the ICS list was the flat, over-wide top level, not the digit count.

Where numeric codes are used, as in the GL and the dimensions, a level that would exceed 9 items is a signal to consider adding a level, not to widen the code. Where a different character set is acceptable, alpha extends a level without lengthening the code.

The only remaining arguments for two digits are interoperability with external standards and client legacy structures. These are not reasons to change Taxonomy BuilderTM, because they are met by cross-mapping.

6. Existing code schemes and cross-mapping

The object of Taxonomy BuilderTM is not to recode existing hierarchies. The ICS example was used only to get a better feel for the issues.

Where an existing code scheme is poorly structured, the ERP Doctor approach allows a precision taxonomy to be developed and then cross-mapped to the existing code scheme, so that precision analysis is retrofitted without disturbing the original. The “ICS field” column in the example above shows this.

7. Rule for Taxonomy BuilderTM

Rule
Taxonomy BuilderTM builds precision taxonomies only: one character per level (numeric, alpha or alphanumeric), 5 to 9 items per level as the guiding target, ALL CAPS structural names and Proper Case posting names. It does not accommodate multi-digit code levels. Existing lists that use them are held separately and, where useful, cross-mapped to a precision taxonomy to retrofit precision analysis.
